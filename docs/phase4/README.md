# 第四阶段：在线交易链路（ICP 经营许可审核关键）

> 依据 `tasks/Task1.md` 第五节。交付日期：2026-11-20
> 验收截图：`docs/phase4/screenshots/`（PC 端 01–12，移动端 m-*）

## 1. 交易流程

```
浏览方案 ─▶ 选版本/数量/增值服务 ─▶ 立即购买 ─▶ 下单页（游客可直接提交）
   ─▶ 生成订单号，跳转支付页 ─▶ 微信 Native 扫码（30 分钟倒计时，每 3 秒查询支付状态）
   ─▶ 微信回调（验签 + 幂等入账）─▶ 支付成功页 + 短信/邮件通知
   ─▶ 后台：已支付 → 服务进行中 → 已完成（每一步可写进度备注，客户在用户中心可见）
```

未支付的订单超过 30 分钟由定时任务自动关闭。关闭前会先向微信查单：如果实际已经付款（只是回调没到），就按已支付入账，不会误关。

## 3. 表结构变更清单（`V1__init_schema.sql` 中的第四阶段部分）

| 表 | 说明 | 关键设计 |
|---|---|---|
| `app_user` | 前台用户 | phone 唯一、username 唯一（可空）、password_hash（**BCrypt**，只用验证码登录的用户可以为空） |
| `orders` | 订单 | **order_no 唯一**（日期时间 14 位 + 业务码 2 位 + 随机数 6 位）；access_token；**total_amount DECIMAL(12,2)**；status；agreement_version；code_url（有效期内复用）；pay_expire_at；**transaction_id 唯一索引（防重复入账的兜底）** |
| `order_item` | 订单明细 | 版本和增值服务各一行，保存下单时的名称、单价、单位**快照**；unit_price 与 amount 都是 DECIMAL |
| `order_log` | 状态流转与服务进度 | 每一次变化都记录 from/to、备注、操作人类型（游客/用户/管理员/系统） |
| `payment_notify` | 支付回调流水 | 每次回调都记录结果：已入账 / 重复 / 拒绝 / 忽略，用于审计和排查 |

订单号示例：`2026112013261701066006` = `20261120132617`（时间）+ `01`（业务码：解决方案在线购买）+ `066006`（随机数）。订单号冲突时自动重试。

## 5. 支付

### 5.1 两种模式（`PAY_MODE` 开关）

| 模式 | 用途 | 说明 |
|---|---|---|
| `mock`（默认） | 开发、演示、审核演示 | 二维码内容是模拟链接；支付页显示"模拟支付成功"按钮，点击后走**与真实回调完全相同的入账逻辑** |
| `wechat` | 生产 | 微信支付官方 SDK `wechatpay-java`（APIv3）的 Native 下单。平台证书自动下载和更新；下单时把 `time_expire` 设为 30 分钟，与本站关单时间一致 |

### 5.2 回调签名验证与幂等

1. **验签**：`NotificationParser` 校验 `Wechatpay-Signature` 等请求头，并用 APIv3 密钥解密报文。验签失败返回 401，不处理。
2. **金额核对**：回调金额（分）必须等于订单金额，否则拒绝入账并记录日志。
3. **幂等**：用一条带条件的 UPDATE 把订单从"待支付或已取消，且尚无交易号"改为"已支付"。只有第一次能改成功（影响 1 行），重复回调影响 0 行，判定为重复：直接返回成功，不重复入账，也不重复发通知。`transaction_id` 上的唯一索引作为兜底。
4. **超时关单后才到账**：仍然入账（钱已经收到），并在订单日志中注明。如果同一订单被另一笔交易再次支付，则拒绝入账并记录错误日志，需人工处理退款。
5. 每次回调都写一条 `payment_notify` 记录。支付成功通知在**事务提交后**异步发送，发送失败不影响入账。

以上逻辑都有集成测试覆盖：重复回调、另一笔交易、金额不符、超时关单后到账、取消后不能再支付。

### 5.3 自动关单

每分钟执行一次，用 Redis 锁保证多实例部署时只有一个实例在跑。处理 `pay_expire_at` 已过期的待支付订单：先查单，已经付了的就入账；确定没付的先调微信关单，再把订单改为"已取消（超时未支付）"；查单失败或用户正在支付（结果不确定）的本轮跳过。

另有每小时一次的对账：最近 48 小时内关闭、生成过二维码但没有交易号的订单再查一遍，实际已付款的恢复为"已支付"。

### 5.4 退款（V4__order_refund.sql）

- **发起**：任一管理员在订单详情页"退款"卡片中操作，原路退回。只有「已支付」「服务中」的订单可退（已完成的不退）；支持部分退款，累计不超过订单金额，全额退完订单变为「已退款」（`REFUNDED`）。退款原因会写入订单进度，客户可见。
- **异常收款**：重复付款、金额不符等被拒绝入账的交易，会在订单详情页以红色提示列出，可"整笔退回"，每笔只能退一次，不影响订单状态。
- **流程**：事务内锁订单行、校验额度、写"退款中"的退款单（额度即被占用）→ 事务外调用微信退款 → 成功/失败立即落库；"处理中"或网络超时的，由退款回调或每 5 分钟的同步任务（按我方退款单号查询）确认。确认成功用带条件的 UPDATE，回调与查单重复确认也只累加一次。
- **失败**：微信明确拒绝（如商户余额不足）的标记为失败、释放额度，可重新发起；退款异常（`ABNORMAL`，如用户银行卡注销）同样标记失败，需在商户平台手动处理。
- **通知**：退款成功后给客户发短信和邮件。后台首页"累计实收"已扣除退款。
- 支付通道切换后（如 mock 收的款、现在是微信），不能原路退回，接口会直接提示。

## 8. nginx 配置变更

- `location ~ ^/(user|order|pay)(/|$)` 返回 `spa.html` 空壳（这些页面不做预渲染）。
- `/api/pay/notify/wechat` 通过 `/api/` 反代到后端。**微信要求回调地址是 HTTPS**。nginx 配置拆为：`cn01-base.inc`（gzip、缓存策略）+ `cn01-site.inc`（站点规则，两阶段共用）+ 入口文件二选一：`cn01.conf`（HTTP 阶段）/ `cn01-https.conf`（HTTPS 阶段：80 跳 443、HSTS、保留 ACME 路径），切换步骤见 `cn01-https.conf` 文件头。
- `robots.txt` 已屏蔽 `/user/`、`/order/`、`/pay/`、`/admin/`、`/api/`。

## 9. 部署

### 9.1 服务器一次性准备

```bash
# 1) MySQL 8：只监听 127.0.0.1
mysql -uroot -p -e "CREATE DATABASE cn01 DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
  CREATE USER 'cn01'@'127.0.0.1' IDENTIFIED BY '强密码'; GRANT ALL ON cn01.* TO 'cn01'@'127.0.0.1';"
# 2) Redis 7：在 redis.conf 中设置 bind 127.0.0.1 和 requirepass 强密码
# 3) 用户、目录、systemd、nginx
sudo ./deploy/server-init.sh
sudo vi /etc/cn01/backend.env        # 按 deploy/backend.env.example 填写密码和密钥
```

### 9.2 发布与回滚

```bash
DEPLOY_HOST=服务器IP DEPLOY_USER=deploy ./deploy/deploy.sh   # 后端 + 前台 + 后台一起发布
DEPLOY_HOST=服务器IP ./deploy/rollback.sh                     # 回滚到上一版本（前后端一起）
DEPLOY_HOST=服务器IP ./deploy/rollback.sh --list
```

发布流程：后端测试并打包 → 前端测试并构建（预渲染时从 `SSG_API_BASE` 取数，默认为线上地址）→ 产物自检 → 上传到新版本目录 → 切换软链接 → 重启后端 → **健康检查最多等 120 秒，失败就自动切回上一版本** → `nginx -t` → 重载 nginx。

已在本地实测：发布成功；用模拟的健康检查失败验证了自动回滚（current 保持在上一版本，脚本退出码为 1）。

**首次部署：** 后端还没上线时，用 `SSG_API_BASE= ./deploy/deploy.sh`（留空），动态内容改由浏览器加载；后端上线后再发布一次，把方案详情页纳入预渲染和 sitemap。

**数据库回滚的约束：** Flyway 迁移只会前进不会回退，所以每次表结构变更都要向前兼容（只加表、加列，不删列、不改名），这样回滚后的旧版本后端也能在新表结构上运行。
